# 선택 대체 입력의 전체 복구 검증

0.3.2-beta.1 빌드 385, 2026-11-14 검증 결과.

선택한 글자를 새 입력으로 바꿀 때 편집기가 이전 본문·선택을 여러 키 동안 보고하면, 복구 후보에서 앞 키가 사라져 잘못 입력된 단어의 일부만 보정되는 문제가 있었다. 385는 같은 본문·선택이 유지되는 동안 앞 키부터 이력을 보존한다. 확인한 Codex 조건에서 영문이 섞여 남던 문제는 단어 전체의 사후 복구로 해결됐다.

## 수정 범위

- 같은 입력칸·입력 소스의 동일한 본문 UTF-16·선택 범위가 유지될 때만 후속 키를 같은 선택 대체 이력에 연결한다.
- 다른 본문·선택이 관측되면 허용을 종료한다. 탐색·삭제·편집 단축키·입력칸·입력 소스·조회 실패·기한에 대한 기존 경계를 유지한다.
- 이력 관측에는 추가 AX 조회·키 보관·재전송·선택 변경을 넣지 않는다. 실제 복구는 전체 관측 키의 출력, 양쪽 기존 본문과 접힌 커서를 검증한 뒤 수행한다.

상세 계약은 [동작 명세](../SPEC.md#선택-대체와-자동-완성), 검사 실행 방법은 [개발 안내](../DEVELOPMENT.md)를 따른다.

## 자동 검사와 실제 IME

| 검사 | 결과 |
| --- | --- |
| 수정 전 대조 | 같은 신규 회귀가 두 번째 키의 이력 보존 검사에서 실패 |
| 선택 대체 신규 회귀 | 342검사 통과: 선택 범위·UTF-16·다섯 배열·문맥 경계·전체 복구와 후속 조합 |
| 기존 불일치 복구 | 43모드와 진단·개인정보 제외 3실행 통과 |
| 전환 대기열 | 2,170검사 통과, 초기 자판 상충과 선택 반영 지연의 네 조합 포함 |
| 기존 선택·편집 | 선택 보존 72, 수동 편집 경계 64, 삭제 후 조합 143검사 통과 |
| 실제 Apple IME | 다섯 배열의 전체·중간 선택 대체 10건, 기존 영문·혼합 복구 11건 통과 |
| 앱 빌드 | 전체 제품 소스 77개 최적화 컴파일과 후보 서명 검증 통과 |

실제 IME 검사는 독립 AppKit 시험창에서 실행했다. 지연된 선택 표본과 영문 출력은 시험용 대역으로 구성하고, 복구와 후속 키는 실제 Apple IME로 전달했다. 이 검사를 타사 편집기의 실제 AX·물리 키 결과로 계산하지 않는다. 외부 입력 개입이 있었던 첫 회차는 제외하고 새 시험창에서 21건을 다시 확인했다. 종료 후 원래 입력 소스·Caps 설정·임시 활성 소스의 복원을 확인했다.

영향 범위의 검사와 전체 제품 컴파일을 수행했으며, 표준 빌드 스크립트에 포함된 모든 비영향 검사를 다시 실행한 것은 아니다.

## 설치한 385의 실제 Codex 물리 키

새 설치본의 권한·감시 활성 확인 후 사용자가 직접 입력했다. 화면 문자열은 사용자 확인이고, 제품 진단에서는 내용·키 값·정확한 선택 좌표를 수집하지 않았다.

1. 영문 상태에서 ABCDEF 입력 → Cmd+A → 한Q 한영키로 두벌식 전환 → 지금과 끝 공백 입력. 사용자가 wlrma이 나타난 뒤 지금으로 전체 보정됐다고 확인했다. 진단에서도 옛 선택 표본이 다섯 키 동안 유지된 상황에서 보정 문자키 다섯 개가 각각 한 번 재입력됐다. 내부 복구 구간은 이 한 회에서 358ms였고, 재시도·실패 없이 보관·대기 입력 0개로 끝났다. 끝 공백과 정확한 커서 위치는 이 첫 보고에서 별도 확정하지 않았다.
2. 시험 글자를 전체 선택해 가나다와 끝 공백으로 바꾼 뒤, 나만 선택해 마로 대체했다. 사용자가 가나다 → 가마다 전체·부분 선택 대체가 모두 정상이라고 확인했다. 후속 진단의 보존 구간에는 자동 복구·보정 재입력·실패가 없고 보관·대기 입력은 0개였다.

이번 조건에서는 앞부분이 빠진 불완전한 보정을 해결하고 기존 선택 대체 동작도 확인했다. 처음 잠깐 영문이 나타날 수 있으며 이후 정상 한글로 복구된다. 최초 영문 출력과 늦은 AX 응답의 원인, 장기간 자연 재발 여부까지 확정한 결과는 아니다.
