# 버전과 변경 이력 관리

## 하나의 버전 원본

루트의 `version.env`를 Git에 커밋한다. 빌드 스크립트는 기존 앱을 읽어 버전을 증가시키지 않는다.

| 필드 | 첫 베타 준비 값 | 용도 |
| --- | --- | --- |
| `APP_VERSION` | `0.1.0` | macOS 표시 버전 (`CFBundleShortVersionString`) |
| `BUILD_NUMBER` | `71` | 업데이트 순서 (`CFBundleVersion`). 배포할 때마다 증가 |
| `RELEASE_VERSION` | `0.1.0-beta.1` | 배포용 베타 식별자와 예정 Release 이름. 번들의 `HanQReleaseVersion`에 기록하며 Git 태그는 앞에 `v`를 붙임 |

기존 로컬 빌드 70 다음으로 71을 사용한다. 71은 첫 공개 후보의 예약 번호이며 이미 공개됐다는 뜻은 아니다. 같은 소스를 다시 빌드해도 번호가 자동 증가하지 않는다. 배포 준비 도중 소스를 수정할 수 있지만, 외부에 전달한 앱과 내용이 달라지면 번호도 올린다.

현재 앱 정보창과 피드백 폼에는 `APP_VERSION`과 `BUILD_NUMBER`를 표시하며, `RELEASE_VERSION`의 `beta.N`은 표시하지 않는다. 베타 식별자까지 앱에 표시하는 작업은 별도로 필요하다.

## 증가 예시

| 배포 | APP_VERSION | BUILD_NUMBER | 태그 |
| --- | --- | --- | --- |
| 첫 베타 | 0.1.0 | 71 | v0.1.0-beta.1 |
| 다음 베타 | 0.1.0 | 72 | v0.1.0-beta.2 |
| 정식 출시 예시 | 1.0.0 | 73 | v1.0.0 |
| 오류 수정 예시 | 1.0.1 | 74 | v1.0.1 |

정식 출시 시점이나 버전이 바뀌어도 빌드 번호를 1로 초기화하지 않는다. 표의 이후 버전은 예시이며 출시 약속이 아니다. 표시 버전은 호환되는 오류 수정은 patch, 기능 추가는 minor, 큰 변경은 major를 올리는 기준으로 관리한다. 베타 단계에서는 `beta.N`도 함께 증가시킨다.

## 배포 기록 규칙

GitHub 머지·업로드, 배포 태그 발행과 Release 생성·공개는 유지관리자가 직접 수행하거나 AI에 요청하여 수행한다. 아래 내용은 배포 기록의 작성 기준이며, 문서 자체가 원격 작업의 실행 요청을 뜻하지는 않는다.

1. 변경마다 의미 있는 커밋을 만들고, 사용자가 체감하는 변경 사항과 배포 시 주의할 사항을 [CHANGELOG](../CHANGELOG.md)의 미배포 항목에 누적한다.
2. 배포 준비 시 `version.env`의 세 값을 확정하고 변경 이력·릴리스 노트와 일치시킨다.
3. 실제 배포일이 정해지면 변경 이력에 날짜를 기록하고, 검증한 커밋에 태그를 붙인다. 초안 단계에서 공개 완료로 쓰지 않는다.
4. CHANGELOG는 간결한 기록체로 작성한다. GitHub Release 본문은 해당 CHANGELOG 항목을 바탕으로 작성한다. 추가·개선·수정, 설치/업데이트 주의 사항, 알려진 제한, 지원 범위, 서명·공증 여부를 적고 해당하지 않는 빈 섹션은 생략한다.
5. 공개한 태그를 이동하거나 같은 파일명으로 다른 앱을 덮어쓰지 않는다. 수정본은 더 높은 빌드 번호와 새 태그로 배포한다.
6. 새 컴퓨터에서도 해당 Git 커밋의 `version.env`를 사용한다. 배포 자동화에는 원격의 마지막 공개 번호보다 큰지, 태그·노트·앱 버전이 일치하는지 확인하는 검사를 추가한다.

현재 구현은 버전 파일 로딩과 형식 검사까지다. 배포 후보와 원격 Release의 버전 비교 검사는 배포 준비 도구에서 구현할 예정이며, 실제 태그·Release 발행은 유지관리자 또는 요청받은 AI가 수행한다. `build-app.sh`로 로컬 앱을 만드는 것만으로 Release가 생성되지는 않는다.
