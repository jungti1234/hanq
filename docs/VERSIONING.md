# 버전과 변경 이력 관리

## 하나의 버전 원본

루트의 `version.env`를 Git에 커밋한다. 빌드 스크립트는 기존 앱을 읽어 버전을 증가시키지 않는다.

| 필드 | 용도 |
| --- | --- |
| `APP_VERSION` | macOS 표시 버전 (`CFBundleShortVersionString`) |
| `BUILD_NUMBER` | 업데이트 순서 (`CFBundleVersion`). 새 검증 후보·배포본마다 증가 |
| `RELEASE_VERSION` | 배포용 버전과 베타 식별자. 번들의 `HanQReleaseVersion`에 기록하며 Git 태그는 앞에 `v`를 붙임 |

현재 버전은 `version.env`, 변경 내용은 CHANGELOG에서 관리한다. 이 문서는 정책이 달라질 때 갱신하며 빌드마다 수정하지 않는다. 아래 번호는 규칙을 설명하기 위한 예시다.

앱 정보창과 피드백 폼에는 `RELEASE_VERSION`과 `BUILD_NUMBER`를 표시해 베타 식별자까지 구분한다.

## 버전을 올리는 기준

작업자는 변경 내용과 기존 공개 여부에 따라 버전 갱신 필요성을 판단하고, 필요한 경우 별도 요청 없이 `version.env`와 변경 이력을 함께 갱신한다. AI에 맡긴 작업에도 같은 기준을 적용한다.

| 구분 | 증가 기준 | 예시 |
| --- | --- | --- |
| patch | 기존 기능의 오류 수정·안정성·보안 개선 | `1.0.0` → `1.0.1` |
| minor | 사용자에게 제공하는 기능 추가 | `0.1.0` → `0.2.0` |
| major | 첫 정식 출시 또는 이후 큰 호환성 변경 | `0.x.y` → `1.0.0` |
| `beta.N` | 같은 목표 버전에서 다음 공개 베타 배포 | `0.1.0-beta.1` → `0.1.0-beta.2` |
| 빌드 번호 | 변경된 앱을 별도 실행·검증 후보 또는 배포본으로 식별할 때 | `100` → `101` |

- 아직 공개하지 않은 목표 버전 안에서 진행하는 구현은 해당 버전에 누적한다. 첫 공개 전 업데이트 기능·DMG 도구를 구현해도 작업마다 `0.2.0`, `0.3.0`으로 올리지 않는다.
- 첫 공개 후 기능 추가는 다음 minor, 오류 수정만 있으면 다음 patch를 목표로 한다. 해당 버전의 베타를 배포할 때는 `-beta.1`부터 시작한다.
- 같은 공개 베타를 준비하는 로컬 후보는 빌드 번호로 구분한다. 예를 들어 `0.1.0-beta.1`의 후보를 빌드 100·101로 구분하며, 로컬 빌드마다 `beta.N`을 증가시키지 않는다.
- 커밋·동일 입력의 재빌드·문서만의 수정에는 번호를 올리지 않는다. 앱 코드·리소스·의존성·배포 빌드 설정이 달라진 후보를 새로 검증할 때는 이전 후보와 다른 빌드 번호를 사용한다.
- 빌드 번호는 beta·정식·major/minor 변경과 관계없이 계속 증가시키며 1로 초기화하지 않는다. 외부에 전달한 번호는 다른 내용에 재사용하지 않는다.
- 정식 전환은 베타 꼬리표 제거뿐 아니라 출시 준비 상태를 확인하는 결정이다. 실제 공개·정식 전환은 유지관리자의 요청 범위에 따른다.

일반 업데이트는 권장하며, minor나 major가 올라갔다는 이유만으로 구버전 사용을 막지 않는다. 심각한 취약점 등으로 사용 중단이 필요한 경우에는 버전 증가와 별도로 [필수 업데이트 정책](RELEASE.md#필수-업데이트-정책)을 발행한다.

## 배포 기록 규칙

GitHub 머지·업로드, 배포 태그 발행과 Release 생성·공개는 유지관리자가 직접 수행하거나 AI에 요청하여 수행한다. 아래 내용은 배포 기록의 작성 기준이며, 문서 자체가 원격 작업의 실행 요청을 뜻하지는 않는다.

1. 변경마다 의미 있는 커밋을 만들고, 사용자가 체감하는 변경 사항과 배포 시 주의할 사항을 [CHANGELOG](../CHANGELOG.md)의 미배포 항목에 누적한다.
2. 배포 준비 시 `version.env`의 세 값을 확정하고 변경 이력·릴리스 노트와 일치시킨다.
3. 실제 배포일이 정해지면 변경 이력에 날짜를 기록하고, 검증한 커밋에 태그를 붙인다. 초안 단계에서 공개 완료로 쓰지 않는다.
4. CHANGELOG는 간결한 기록체로 작성한다. GitHub Release 본문은 CHANGELOG를 참고해 `docs/releases/<RELEASE_VERSION>.md`에 별도로 작성·검토한다. 내부 개발 이력이나 준비 상태를 그대로 복사하지 않는다. 추가·개선·수정, 설치/업데이트 주의 사항, 알려진 제한, 지원 범위, 서명·공증 여부를 적고 해당하지 않는 빈 섹션은 생략한다.
5. 공개한 태그를 이동하거나 같은 파일명으로 다른 앱을 덮어쓰지 않는다. 수정본은 더 높은 빌드 번호와 새 태그로 배포한다.
6. 새 컴퓨터에서도 해당 Git 커밋의 `version.env`를 사용한다. 배포 도구는 원격 공개 Release보다 빌드 번호가 큰지, 기존 태그와 중복되지 않는지, 노트와 앱 버전이 일치하는지 확인한다.

버전 파일 로딩·형식 검사는 빌드 스크립트에서, 원격 Release의 빌드 번호·태그 중복 검사는 `scripts/release.py draft`에서 수행한다. 실제 태그·Release 발행은 유지관리자 또는 요청받은 AI가 수행한다. `build-app.sh`로 로컬 앱을 만드는 것만으로 Release가 생성되지는 않는다.
