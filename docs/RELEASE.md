# 한Q 배포 안내

이 문서는 배포 파일 준비, GitHub Release 게시, 운영 업데이트 피드와 필수 업데이트 정책 관리 절차를 설명한다.

현재 공개 버전은 [0.3.0-beta.1](https://github.com/jungti1234/hanq/releases/tag/v0.3.0-beta.1)(빌드 148)이다. 소스 문서나 릴리스 노트 초안을 수정하는 것만으로 공개 릴리스·운영 피드가 바뀌지는 않는다.

### 코드 서명과 권한

공개 0.2.0은 ad-hoc 서명이며, 0.3.0부터 동일 자체 서명 인증서를 사용한다. `--signing-identity` 또는 `HANQ_SIGNING_IDENTITY`로 같은 인증서 지문을 명시한다. 생략하면 기본 빌드는 ad-hoc이다. `release.py`가 기록한 실제 서명 방식·인증서 지문·코드 식별 조건을 준비한 앱과 대조한다.

자체 서명은 Developer ID 서명·공증을 대신하지 않는다. 최초 다운로드의 Gatekeeper 실행 차단과 기존 ad-hoc 앱에서 전환할 때의 손쉬운 사용 재승인 가능성을 설치 안내에 명시한다. 같은 인증서의 권한 재사용 조건과 확인 절차는 [개발 안내](DEVELOPMENT.md#검증된-동일-인증서의-권한-재사용)를 따른다.

## 작업 범위와 담당

유지관리자가 배포 커밋·산출물·검증 결과를 확인하고 원격 게시와 운영 업데이트 피드 반영을 담당한다. 로컬 준비와 원격 게시 명령은 구분한다. 로컬 개발 빌드의 ad-hoc 서명은 Developer ID 배포 서명과 다르다.

## 버전과 변경 이력

[버전 관리 규칙](VERSIONING.md)에 따라 `version.env`의 배포 값을 확정하고, [CHANGELOG](../CHANGELOG.md)를 참고해 `docs/releases/<RELEASE_VERSION>.md`에 공개용 릴리스 노트를 작성한다. 첫 줄은 `# 한Q <RELEASE_VERSION>`으로 맞추고, 사용자에게 필요한 기능·설치 안내·알려진 제한을 정리한다. 내부 후보 빌드 이력과 준비 작업은 그대로 옮기지 않는다.

게시 전에 GitHub Markdown 렌더링 결과와 업데이트 창용 HTML을 확인한다. `**업데이트 확인…**으로`처럼 문장부호 뒤에 조사가 붙으면 별표가 그대로 표시될 수 있으므로, 렌더링된 본문에 남은 Markdown 기호를 점검하고 `<strong>` 또는 일반 문구로 수정한다.

업데이트 창용 HTML은 밝은 모드·다크 모드에서 본문·링크·인라인 코드의 대비를 확인한다. 다크 모드에서 글자가 어둡게 고정되지 않도록 테마에 맞는 색상을 사용한다.

## 배포 구성

| 구성 | 역할 및 상태 |
| --- | --- |
| GitHub 소스 저장소 | [jungti1234/hanq](https://github.com/jungti1234/hanq) 공개 저장소에서 관리 |
| GitHub Releases | 베타 설치 파일과 릴리스 노트 제공 |
| DMG | 앱과 Applications 바로가기를 포함한 설치 이미지 |
| Sparkle 2.10.0 | 업데이트 조회·다운로드·서명 검증·설치·재실행 |
| HTTPS appcast | GitHub Pages에 빌드 148 및 업데이트 창용 릴리스 노트 게시 |
| 서명된 업데이트 정책 | 최소 허용 빌드·적용 대상·사유·시점을 관리. GitHub Pages에 별도 파일 게시. 현재 제한 규칙 없음 |

한Q는 단일 앱을 복사해 사용하는 구조이므로 PKG는 현재 필요하지 않다. DMG에서 Applications로 복사한 뒤 실행하도록 안내한다. GitHub의 자동 생성 `Source code (zip)`은 실행 앱이 아니다.

첫 베타는 ad-hoc 서명으로 배포했으며, 정식 출시 전 베타 단계에서 Developer ID 서명·공증을 적용할 계획이다. 최초 다운로드의 macOS 실행 차단 가능성과 설치 시 필요한 손쉬운 사용 권한을 배포 안내에 명시한다. Sparkle 업데이트 서명은 Apple 서명·공증과 별개다. Developer ID·공증을 도입할 때는 새 서명 구성으로 설치·업데이트·권한 유지 여부를 다시 검증한다.

## Sparkle 연동 기준

- 검증한 Sparkle 버전을 고정하고 프레임워크·실행 권한·심볼릭 링크를 보존한다. 앱 번들에 포함하고 링크·실행 시 검색 경로·서명을 검증한다.
- `SPUStandardUpdaterController`를 주 UI 인스턴스에만 연결한다. 권한 검사·복구용 보조 프로세스에서 updater를 시작하지 않는다.
- 업데이트 메뉴와 `canCheckForUpdates` 상태를 연결한다. 현재 메뉴는 자동 활성화가 꺼져 있으므로 상태를 명시적으로 반영한다.
- `SUFeedURL`과 공개키 `SUPublicEDKey`를 앱에 포함하고 배포 설정과 일치하는지 확인한다. 개인키는 저장소에 넣지 않고 안전하게 백업한다.
- 초기 정책은 자동 새 버전 확인과 사용자 확인 후 설치·재실행이다. 업데이트 확인 설정을 제공한다.
- 업데이트 종료가 watchdog·권한 복구의 자동 재실행과 충돌하지 않게 검증한다. 앱 이름·번들 ID·설치 위치를 유지한다.
- 프레임워크 및 포함 구성요소의 라이선스 고지를 보존한다.

GitHub의 Pre-release 표시는 Sparkle 채널을 분리하지 않는다. 베타·안정판 도입 시 피드 또는 채널 정책을 명시적으로 구성한다.

## 필수 업데이트 정책

현재 운영 정책은 빈 규칙 목록이며 어느 빌드도 차단하지 않는다. 필수 업데이트는 아래 기준에 따라 앱에서 별도로 최소 허용 빌드와 기능 제한을 관리한다. Sparkle의 중요 업데이트 표시만으로 한Q 기능이 중단되지는 않는다. 정책 확인 기능이 없는 구버전에는 나중에 정책을 발행해도 제한을 적용할 수 없다.

정책 동작의 자동 검사와 별도 앱 시험 방법은 [개발 안내](DEVELOPMENT.md#별도-후보-빌드와-업데이트-의존성)를 따른다. 시험 응답으로 확인한 제한·복귀 결과를 운영 HTTPS 정책과 실제 한Q 입력 복귀까지 검증한 것으로 간주하지 않는다.

최소 허용 빌드는 GitHub Pages에 게시하는 별도의 서명된 업데이트 정책 파일에서 관리한다. 앱에는 정책 조회 주소와 검증용 공개키를 포함하고, 최소 허용 빌드 값 자체는 고정하지 않는다. 정책 원본과 변경 이력은 공개 저장소에서 관리하며 개인키는 저장소 밖의 안전한 인증 저장소에 보관한다. 공개 주소와 검증키는 `updates/config.json`, 정책 원본은 `updates/policy-source.json`, 게시할 파일은 `updates/site/`에서 관리한다.

유지관리자가 정책 후보를 작성하고, 수정된 앱 공개 → 실제 다운로드·업데이트 경로 검증 → 정책 서명·게시 순으로 적용한다. 예를 들어 보안 수정본이 빌드 85라면 해당 범위의 최소 허용 빌드를 85로 지정해 84 이하를 제한할 수 있다. 이 값은 일반 Release 발행이나 버전 증가와 연동해 자동으로 올라가지 않는다. 오발행 시에는 제한을 철회한 새 서명 정책을 게시하며, 앱은 다음 유효한 정책 확인에서 제한을 해제한다.

- 앱 실행 및 업데이트 확인 시 HTTPS로 정책을 조회한다. 조회는 입력 처리를 막지 않는 비동기로 수행하고 시간 제한을 둔다. 일반 새 버전 자동 확인을 끈 경우에도 실행 시 필수 정책 조회는 수행하며, 이 차이를 사용자에게 안내한다.
- 정책은 최소 허용 빌드, 적용 채널·OS·아키텍처 범위, 사유, 적용 시점, 정책 유효 기간과 업데이트 대상을 명시한다. 배포자가 서명한 정책의 진위와 유효성을 검증하고, 정책 서명과 다운로드 앱의 서명을 각각 확인한다.
- 온라인에서 유효한 정책을 확인했고 현재 빌드가 적용 대상의 최소 허용 빌드보다 낮으면 한Q의 키 매핑·변환 기능을 중단한다. 사유와 필요한 버전을 안내하며 업데이트·재확인·종료 경로를 제공한다. 안내창을 닫거나 업데이트 설치를 취소해도 기능이 다시 켜지지 않는다.
- 기능을 중단할 때 이벤트 탭·대기 중인 편집·눌린 키 상태를 안전하게 정리한다. macOS 기본 입력과 다른 앱의 사용, 저장된 한Q 설정은 유지한다. watchdog·권한 복구가 제한을 우회해 기능을 다시 켜지 않도록 한다.
- 인터넷 차단·시간 초과·서버 장애·잘못된 서명 등으로 유효한 정책을 확인하지 못하면 사용을 허용한다. 과거 정책을 저장해 두었다는 이유로 오프라인 실행을 차단하지 않는다. 이미 제한된 상태에서도 재확인 결과가 오프라인·조회 실패라면 제한을 해제한다. 기능 복귀 시 기존 권한·안전 조건을 다시 확인한다.
- 적용 대상에서 설치 가능한 업데이트가 실제로 공개된 뒤 정책을 발행한다. 지원 OS·아키텍처에 맞는 업데이트 경로가 없거나 정책에 모순이 있으면 제한하지 않는다. 다운로드 실패·서명 불일치 시 손상된 앱을 설치하지 않으며, 재시도·정책 재확인·종료 경로를 유지한다.
- 일반적인 기능 추가·버전 증가만으로 최소 허용 빌드를 자동으로 올리지 않는다. 심각한 취약점 대응 등 사용 중단이 필요한 경우 유지관리자가 적용 대상·시점을 지정하고 정책을 발행한다.

베타 종료도 별도 정책으로 처리한다. `1.0.0`이 공개되었다는 사실만으로 모든 베타를 즉시 차단하지 않고, 정식 출시 시 베타 대상과 전환 유예 기간을 정해 공지한다. 긴급 보안 업데이트는 별도로 즉시 적용할 수 있다. 두 경우 모두 위 오프라인 사용 허용 기준을 따른다.

검증에는 최소 허용 빌드의 미만·동일·초과, 적용 범위·시점·유효 기간, 정책 서명 오류, 오프라인 시작·제한 후 연결 실패, 정책 철회, 설치 취소·실패, 기능 중단·복귀와 실제 업데이트 후 제한 해제를 포함한다.

## 정책 파일 관리

- 피드: `https://jungti1234.github.io/hanq/appcast.xml`
- 정책: `https://jungti1234.github.io/hanq/policy.json`
- 게시 위치: 공개 저장소의 `gh-pages` 브랜치 루트. `main`에 문서를 커밋하는 것만으로 정책이 게시되지는 않는다.
- 정책 형식: `schemaVersion`, `bundleIdentifier`, UTC `issuedAt`·`expiresAt`, `rules` 목록. 각 규칙은 `channel`, `architecture`, `minimumOS`, 선택적 `maximumOS`, `minimumBuild`, `effectiveAt`, `reason`, `targetBuild`, `targetVersion`, `downloadURL`을 포함한다. OS 범위는 양끝 포함이며 버전 숫자 순서로 비교한다.
- 서명: 원본 JSON 바이트를 Ed25519로 서명해 base64 `payload`·`signature` 봉투로 게시한다. 현재는 beta/stable, arm64와 해당 GitHub 저장소의 HTTPS Release dmg/zip 주소만 허용한다.

정책 변경은 원본 수정 → 공개 설치 경로·지원 범위 검증 → `bash scripts/policy-tool.sh sign updates/policy-source.json updates/site/policy.json` → 서명 검증 → `gh-pages` 게시 → 실제 HTTPS 응답 검증 순으로 수행한다. 서명 명령은 게시하지 않는다. 규칙을 비운 새 정책으로 제한을 철회할 수 있다. 정책에는 유효 기간이 있으므로 만료되기 전에 갱신하며, 앱은 만료된 정책으로 사용을 제한하지 않는다.

정책 키는 키체인의 서비스 `taek.in.hanq.update-policy` / 계정 `ed25519`, Sparkle 키는 `generate_keys --account taek.in.hanq`로 관리한다. `bash scripts/policy-tool.sh public-key`는 공개키만 출력한다. 키체인을 삭제하거나 Mac을 이전하기 전에 개인키의 안전한 백업·복구를 별도로 준비해야 한다. 개인키를 저장소·로그·릴리스 첨부 파일에 넣지 않는다.

## 매번 배포할 때의 절차

다음은 유지관리자가 수행할 배포 절차다. 로컬 준비와 GitHub Draft 생성은 별도 명령이다.

```sh
bash scripts/build-app.sh --candidate --signing-identity <인증서의-40자리-SHA1>
python3 -m pip install --target .build/dmg-design-tools -r packaging/dmg/requirements.txt
python3 scripts/release.py prepare
# 변경 검토·커밋·푸시 후, 검증한 산출물로 비공개 초안 생성
python3 scripts/release.py draft <prepare가-출력한-산출물-경로>
```

`<…>` 표시는 실제 인증서 지문·산출물 경로로 바꾼다. 이번 `prepare`가 출력한 경로를 사용하고, `version.env`의 버전·빌드 번호와 일치하는지 확인한다.

`prepare`는 해당 버전의 릴리스 노트가 있고 제목의 버전이 일치하는지 먼저 확인한다. CHANGELOG에서 본문을 자동 생성하지 않는다. 업데이트 창용 `updates/site/release-notes/<버전>.html`도 준비해야 하며 appcast의 `sparkle:releaseNotesLink`로 연결한다. 미배포 노트에는 Markdown과 HTML 모두 초안 상태를 표시하고, 실제 공개 직전에 두 본문의 초안 표시를 함께 제거하고 내용을 대조한다. 피드 게시 시 해당 HTML을 함께 게시하고 실제 HTTPS 응답을 확인한다. 후보 앱과 현재 빌드 입력 해시가 일치하는지 확인하고, 개발 빌드는 거부한다. 승인된 로고·설치 안내·버전 표시 디자인의 HFS+·ULFO DMG를 생성해 읽기 전용 마운트·앱 서명·실행 파일 일치·Applications 링크를 확인한 뒤 Sparkle 서명과 체크섬을 검증한다. `dist/<버전>-build<번호>/`에 DMG·SHA256SUMS·release-metadata.json·release-notes.md·appcast-candidate.xml을 남긴다. 기존 산출물 디렉터리는 덮어쓰지 않는다.

노트를 수정한 경우 검토한 원본을 산출물의 `release-notes.md`에도 반영한다. `draft`는 두 파일이 다르면 중단한다. 기존 Draft의 본문 수정은 `gh release edit <태그> --notes-file docs/releases/<버전>.md`로 수행하며 공개 상태는 변경하지 않는다.

`draft`는 작업 트리가 깨끗하고 빌드 입력이 추적된 커밋과 일치하는지, DMG가 변하지 않았는지, 원격에 커밋이 있는지 검사한다. 기존 태그·Release를 재사용하지 않으며 공개 Release보다 빌드가 높은지 확인한다. 검증한 파일을 Draft로 첨부할 뿐 공개하거나 운영 appcast를 수정하지 않는다. 원격의 예전 파일명에서 빌드 번호를 판독할 수 없으면 수동 검토를 위해 중단한다.

1. 배포 커밋·버전·빌드 번호·베타 여부·릴리스 노트를 확정한다.
2. 별도 출력 폴더에서 빌드와 자동 검사를 실행하고 앱 번들과 서명을 검증한다.
3. 공증을 적용하는 배포에서는 Hardened Runtime·포함 코드 서명·공증 제출·티켓 부착·Gatekeeper 평가를 수행한다.
4. 최종 DMG를 완성한 후 SHA-256·Sparkle 서명·appcast 후보를 생성한다. 파일을 수정하면 다시 계산·서명한다.
5. 정확한 커밋의 태그에 Draft Release를 만들고 DMG·체크섬·릴리스 노트를 첨부한다.
6. 버전·커밋·지원 환경·서명/공증 상태·검사 결과·산출물을 확인한 후 공개한다. 승인 후 다시 빌드하지 않고 검증한 파일을 공개한다.
   공개 시 소개 사이트의 다운로드 링크와 버전 표시를 새 Release에 맞춘다. README의 다운로드·변경 내역 링크는 특정 버전에 고정하지 않고, 현재 공개된 기능의 사용법·동작 조건을 안내한다. README의 다음 업데이트 예정 표시와 릴리스 노트의 초안 표시를 정리하며, 버전별 추가·개선 내역은 CHANGELOG와 릴리스 노트에 기록한다. CHANGELOG에 실제 공개일·빌드 번호·배포 상태를 반영한다. 공개되기 전에는 기존 공개본의 다운로드 링크를 유지하며 새 기능을 다운로드 가능한 것으로 표시하지 않는다.
7. 비로그인 환경에서 실제 다운로드 주소·파일 크기·체크섬을 검증한다.
8. 검증에 성공한 뒤 운영 appcast를 발행한다. Draft의 비공개 첨부 파일 주소를 운영 피드에 먼저 게시하지 않는다.

배포 자동화에서도 검증된 산출물과 게시 대상을 확인하고 준비·서명·공개 단계를 구분한다. 키·토큰은 보호된 인증 저장소에서 관리하고 빌드 로그에 출력하지 않는다.

## 설치와 업데이트 검증

0.3.0 베타의 물리 키 실사용 확인은 배포 후 사용자 피드백으로 보완한다. 운영 방식은 [베타 검증 운영](DEVELOPMENT.md#베타-검증-운영)을 따른다. 이는 아래 배포 파일의 설치·업데이트 검사와 별개이며, 실제 배포는 유지관리자의 요청 시 진행한다.

### 소개 사이트 관리

소개 페이지 원본은 `updates/site/index.html`, `styles.css`, `header.css`, `site.js`, `assets/`에서 관리한다. 이용 조건 페이지는 열 때마다 `terms.js`가 공개 저장소 `main`의 `LICENSE`를 가져와 표시한다. LICENSE를 main에 푸시하면 사이트 재배포 없이 다음 페이지 로드부터 반영되며, GitHub 원문 제공 측의 캐시로 반영이 지연될 수 있다. 조회 실패 시 예전 사본 대신 재시도·원문 링크를 안내한다. 사이트 게시 시 `terms.html`, `terms.css`, `terms.js`도 함께 반영한다. 로컬 미리보기는 `python3 -m http.server 8765 --bind 127.0.0.1 --directory updates/site`로 실행한다. 게시할 때는 이 페이지 파일과 자산을 `gh-pages` 브랜치 루트에 함께 반영한다. 소개 페이지만 변경할 때는 `appcast.xml`과 `policy.json`을 수정하지 않는다. 사이트 문구·디자인 변경만으로 앱 버전이나 빌드 번호를 올리지 않는다.

### 앱 설치 및 업데이트

- 브라우저로 내려받은 실제 배포 파일에서 최초 실행·Applications 설치·손쉬운 사용 허용·로그인 실행을 확인한다.
- 구버전→신버전의 다운로드·서명 검증·교체·재실행과 설정 보존을 확인한다.
- 손쉬운 사용 권한 유지 여부, 권한 없는 상태의 업데이트 안내, 검사 helper의 동작을 확인한다.
- 다운로드 실패·서명 불일치·취소 시 기존 앱 파일과 macOS 기본 키 입력이 보존되는지 확인한다. 일반 업데이트는 한Q 기능도 유지하며, 필수 업데이트는 위 정책에 따라 제한한다.
- DMG의 읽기 전용 위치에서 실행했을 때 설치 안내와 업데이트 동작을 확인한다.
- 최소 OS 설정을 실제 실행 검증으로 표현하지 않는다. 확인 환경과 남은 호환성 항목은 [개발 안내](DEVELOPMENT.md)를 따른다.
- 업데이트 확인에 사용하는 네트워크 요청을 사용자 안내에 반영하고 불필요한 시스템 프로필 전송은 켜지 않는다.

문제가 있는 업데이트는 피드에서 제거해 추가 설치를 중단한다. 이미 업데이트한 앱이 자동으로 다운그레이드되지는 않으므로 수정본은 더 높은 빌드 번호로 배포한다. 과거 산출물·체크섬·서명 자료를 보존한다.
