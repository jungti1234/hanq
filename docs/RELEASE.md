# 한Q 배포 안내

이 문서는 배포 구성과 준비 절차를 설명한다. 현재 로컬 앱 빌드와 버전 형식 검사는 구현되어 있으며, Sparkle 연동·DMG 생성·배포 후보 준비 도구는 아직 구현하지 않았다. 공개 다운로드는 제공하지 않는다.

## 작업 범위와 담당

GitHub 머지·업로드, 배포 태그 발행, 배포용 서명·공증, Draft Release 생성·업로드·공개, 운영 업데이트 피드 반영은 유지관리자가 직접 수행하거나 AI에 요청하여 수행한다. 기여자와 AI는 요청받은 구현·문서 작성·로컬 검사와 배포 후보·릴리스 노트 준비를 수행한다. 원격 변경·실제 배포와 그 자동화 실행도 사용자가 요청한 범위에서 수행할 수 있다. 문서에 절차가 있다는 사실만으로 실행을 요청받은 것으로 해석하지 않는다.

로컬 개발 빌드에 포함된 ad-hoc 서명은 개발·검증용이며 Developer ID 배포 서명과 구분한다. 아래 절차는 유지관리자 또는 요청받은 AI가 배포할 때 사용하는 안내다.

## 버전과 변경 이력

[버전 관리 규칙](VERSIONING.md)에 따라 `version.env`의 배포 값을 확정하고, [CHANGELOG](../CHANGELOG.md)의 해당 버전 항목을 릴리스 노트로 준비한다.

## 배포 구성

| 구성 | 역할 및 상태 |
| --- | --- |
| GitHub 소스 저장소 | [jungti1234/hanq](https://github.com/jungti1234/hanq) 공개 저장소에서 관리 |
| GitHub Releases | 설치 파일과 릴리스 노트를 제공할 예정 |
| DMG | 앱과 Applications 바로가기를 담아 설치와 업데이트에 함께 사용할 예정 |
| Sparkle 2 | 앱 내부의 업데이트 조회·검증·교체·재실행. 미구현 |
| HTTPS appcast | 새 버전·다운로드 주소·서명·최소 OS 정보를 제공. GitHub Pages 사용 예정 |

한Q는 단일 앱을 복사해 사용하는 구조이므로 PKG는 현재 필요하지 않다. DMG에서 Applications로 복사한 뒤 실행하도록 안내한다. GitHub의 자동 생성 `Source code (zip)`은 실행 앱이 아니다.

첫 베타는 ad-hoc 서명으로 준비하고, 정식 출시 전 베타 단계에서 Developer ID 서명·공증을 적용할 계획이다. 최초 다운로드의 macOS 실행 차단 가능성과 설치 시 필요한 손쉬운 사용 권한을 배포 안내에 명시한다. Sparkle 업데이트 서명은 Apple 서명·공증과 별개다. Developer ID·공증을 도입할 때는 새 서명 구성으로 설치·업데이트·권한 유지 여부를 다시 검증한다.

## 배포 기능 구현 순서

1. 공개 문서와 소스를 정리하고 Git 저장소·첫 커밋을 준비한다.
2. Sparkle·업데이트 피드·메뉴를 연동한다. 필요한 arm64 지정·빌드 출력 분리·의존성 버전 고정을 함께 정비한다.
3. DMG 후보 생성, 검사 결과 요약, 릴리스 노트·appcast 후보 생성을 도구화한다. GitHub Draft 생성·업로드는 유지관리자 또는 요청받은 AI가 수행한다.
4. 아래 검증 기준에 맞춰 배포 준비 도구를 완성하고, 실제 공개 작업은 유지관리자 또는 요청받은 AI가 수행한다.

## Sparkle 연동 기준

- 검증한 Sparkle 버전을 고정하고 프레임워크·실행 권한·심볼릭 링크를 보존한다. 앱 번들에 포함하고 링크·실행 시 검색 경로·서명을 검증한다.
- `SPUStandardUpdaterController`를 주 UI 인스턴스에만 연결한다. 권한 검사·복구용 보조 프로세스에서 updater를 시작하지 않는다.
- 업데이트 메뉴와 `canCheckForUpdates` 상태를 연결한다. 현재 메뉴는 자동 활성화가 꺼져 있으므로 상태를 명시적으로 반영한다.
- 실제 배포 주소가 준비되면 `SUFeedURL`과 공개키 `SUPublicEDKey`를 앱에 포함한다. 개인키는 저장소에 넣지 않고 안전하게 백업한다.
- 초기 정책은 자동 새 버전 확인과 사용자 확인 후 설치·재실행이다. 업데이트 확인 설정을 제공한다.
- 업데이트 종료가 watchdog·권한 복구의 자동 재실행과 충돌하지 않게 검증한다. 앱 이름·번들 ID·설치 위치를 유지한다.
- 프레임워크 및 포함 구성요소의 라이선스 고지를 보존한다.

현재 앱에는 updater가 없으므로 첫 Sparkle 포함 버전은 직접 설치해야 한다. GitHub의 Pre-release 표시는 Sparkle 채널을 분리하지 않는다. 베타·안정판 도입 시 피드 또는 채널 정책을 명시적으로 구성한다.

## 매번 배포할 때의 절차

다음은 유지관리자 또는 요청받은 AI가 수행할 배포 절차다. 로컬 준비 도구는 산출물·검사 결과·초안을 만들도록 구성하며, 현재 사용할 수 있는 단일 배포 명령은 없다.

1. 배포 커밋·버전·빌드 번호·베타 여부·릴리스 노트를 확정한다.
2. 별도 출력 폴더에서 빌드와 자동 검사를 실행하고 앱 번들과 서명을 검증한다.
3. 공증을 적용하는 배포에서는 Hardened Runtime·포함 코드 서명·공증 제출·티켓 부착·Gatekeeper 평가를 수행한다.
4. 최종 DMG를 완성한 후 SHA-256·Sparkle 서명·appcast 후보를 생성한다. 파일을 수정하면 다시 계산·서명한다.
5. 정확한 커밋의 태그에 Draft Release를 만들고 DMG·체크섬·릴리스 노트를 첨부한다.
6. 버전·커밋·지원 환경·서명/공증 상태·검사 결과·산출물을 확인한 후 공개한다. 승인 후 다시 빌드하지 않고 검증한 파일을 공개한다.
7. 비로그인 환경에서 실제 다운로드 주소·파일 크기·체크섬을 검증한다.
8. 검증에 성공한 뒤 운영 appcast를 발행한다. Draft의 비공개 첨부 파일 주소를 운영 피드에 먼저 게시하지 않는다.

초기에는 로컬 Mac에서 준비 작업을 도구화한다. 향후 GitHub Actions를 도입하면 유지관리자가 직접 실행하거나 AI에 요청해 실행할 수 있다. 머지·배포용 서명·공증·공개·운영 피드 반영의 자동화 범위는 사용자의 요청에 따른다. 키·토큰은 보호된 인증 저장소에서 관리하고 빌드 로그에 출력하지 않는다.

## 설치와 업데이트 검증

- 브라우저로 내려받은 실제 배포 파일에서 최초 실행·Applications 설치·손쉬운 사용 허용·로그인 실행을 확인한다.
- 구버전→신버전의 다운로드·서명 검증·교체·재실행과 설정 보존을 확인한다.
- 손쉬운 사용 권한 유지 여부, 권한 없는 상태의 업데이트 안내, 검사 helper의 동작을 확인한다.
- 다운로드 실패·서명 불일치·취소 시 기존 앱과 키 입력 동작이 보존되는지 확인한다.
- DMG의 읽기 전용 위치에서 실행했을 때 설치 안내와 업데이트 동작을 확인한다.
- 최소 OS 설정을 실제 실행 검증으로 표현하지 않는다. 확인 환경과 남은 호환성 항목은 [개발 안내](DEVELOPMENT.md)를 따른다.
- 업데이트 확인에 사용하는 네트워크 요청을 사용자 안내에 반영하고 불필요한 시스템 프로필 전송은 켜지 않는다.

문제가 있는 업데이트는 피드에서 제거해 추가 설치를 중단한다. 이미 업데이트한 앱이 자동으로 다운그레이드되지는 않으므로 수정본은 더 높은 빌드 번호로 배포한다. 과거 산출물·체크섬·서명 자료를 보존한다.
